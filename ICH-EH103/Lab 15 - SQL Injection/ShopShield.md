# ShopShield — SQL Injection & Cross-Site Scripting Security Testing

**Project:** ShopShield E-commerce Security Assessment  
**Focus Areas:** SQL Injection (SQLi) and Cross-Site Scripting (XSS)  
**Environment:** Isolated staging environment  
**Testing Platform:** Kali Linux  
**Primary Tools:** Burp Suite Community Edition, Firefox Developer Tools, `curl`  
**Application Stack:** React, Supabase, PostgreSQL, Cloudflare Workers  
**Status:** Testing documentation and assessment workflow

---

## 1. Project Overview

This project documents a controlled security assessment of the ShopShield e-commerce application, focusing on SQL injection and cross-site scripting vulnerabilities.

The assessment aims to identify unsafe input handling, database query construction weaknesses, and insecure rendering of user-controlled content. Findings will be documented with reproducible evidence, remediation recommendations, and retest results.

All active vulnerability testing must take place against the dedicated staging application with synthetic data and a separate Supabase test project.

### Objectives

- Identify input fields and endpoints that accept user-controlled data.
- Assess whether application inputs are handled safely by server-side code.
- Investigate potential SQL injection weaknesses.
- Investigate reflected and stored XSS risks.
- Review relevant application code and database access patterns.
- Capture sanitized evidence for reproducibility.
- Recommend and validate remediation measures.
- Maintain a clear separation between production and staging environments.

## 2. Scope and Authorization

### In scope

Testing is limited to the explicitly authorized ShopShield staging environment:

- Product search and filtering.
- Authentication input handling using test accounts.
- Product reviews containing synthetic content.
- Contact forms containing synthetic content.
- Other application endpoints explicitly approved for assessment.
- Relevant frontend components, server-side handlers, and database functions.

### Out of scope

The following activities are prohibited during this assessment:

- Testing against the live production application.
- Accessing real customer records or credentials.
- Extracting database contents or password hashes.
- Modifying real orders, payments, or customer accounts.
- Persistent executable payloads that could affect other users.
- Denial-of-service testing or high-volume automated scanning.
- Accessing systems or endpoints outside the authorized scope.

**Authorization requirement:** Confirm that the staging app uses a separate Supabase project before active testing. Never assume that a copied source-code directory automatically creates an isolated backend.

## 3. Environment Architecture

The intended architecture separates the production application from the testing environment.

```text
                    ShopShield
                        |
             +----------+----------+
             |                     |
       Production              Staging
             |                     |
      Production Worker      Staging Worker
             |                     |
      Production Supabase    Test Supabase
             |                     |
       Real customer data    Synthetic test data
```

The staging Worker and test database must use separate configuration values and credentials. The staging application must not be able to write to production.

### Pre-test isolation checklist

- [ ] Staging source code is stored separately from production.
- [ ] Staging has its own deployment or local test server.
- [ ] Staging uses a separate Supabase project.
- [ ] Staging environment variables point to the test project.
- [ ] Only synthetic test accounts and records are used.
- [ ] Production credentials are not present in staging configuration.
- [ ] No service-role key is exposed to browser code.
- [ ] The target hostname and approved routes are documented.

## 4. Testing Tools

### Kali Linux

Kali Linux is used as the assessment workstation.

### Burp Suite Community Edition

Burp Suite supports manual HTTP request inspection and replay.

Key features used:

- **Proxy → HTTP history:** Review requests generated by the application.
- **Proxy → Intercept:** Inspect requests when necessary.
- **Repeater:** Replay modified requests and compare responses.
- **Target → Site map:** Review observed application routes.

### Firefox Developer Tools

Firefox Developer Tools helps examine:

- DOM rendering.
- JavaScript console errors.
- Network requests and responses.
- HTML attributes and rendered content.
- Whether untrusted content is treated as text or markup.

### curl

`curl` is useful for checking connectivity and inspecting HTTP response headers.

Example:

```bash
curl -I https://YOUR-STAGING-HOSTNAME/
```

Replace the placeholder with the actual staging hostname. Do not substitute the production hostname for active vulnerability testing.

## 5. Burp Suite Setup

1. Open Burp Suite in Kali Linux.
2. Select **Temporary project**.
3. Choose **Use Burp defaults**.
4. Start Burp Suite.
5. Open **Proxy → Intercept** and leave interception off for normal browsing.
6. Configure the dedicated testing browser to use the local Burp proxy, commonly `127.0.0.1:8080`.
7. Open the staging application in that browser.
8. Navigate through the application using synthetic test data.
9. Open **Proxy → HTTP history** and identify requests associated with the authorized routes.

If HTTPS interception is required, configure Burp's CA certificate in the dedicated testing browser. Do not disable certificate validation globally.

### Sending a request to Repeater

1. Locate the relevant staging request in HTTP history.
2. Right-click the request.
3. Select **Send to Repeater**.
4. Open the Repeater tab.
5. Record the original request and response as the baseline.
6. Change only the test parameter under investigation.
7. Send the request and compare the result with the baseline.

Keep the hostname, route, method, and parameter names documented so the test can be reproduced.

# 6. SQL Injection Assessment

## 6.1 What is SQL injection?

SQL injection occurs when untrusted input is incorporated into a database query in a way that changes the intended query structure.

Potential consequences include unauthorized data access, authentication bypass, and unauthorized data modification. Actual impact depends on the vulnerable code, database permissions, and application controls.

## 6.2 Identify candidate input points

Inspect the staging application for:

- Product search.
- Product filtering and sorting.
- Login and registration handlers.
- Product review submission.
- Contact form submission.
- Server-side endpoints that query the database using supplied parameters.

Not every input field interacts with SQL. Trace the request to its actual handler before classifying a potential vulnerability.

## 6.3 Establish a baseline

1. Open the staging application.
2. Navigate to product search.
3. Search for an ordinary value such as `shirt`.
4. Record the request method, route, parameter name, HTTP status, and response behavior.
5. Repeat the request to establish that the behavior is consistent.
6. Save sanitized evidence as `SQLI-01-baseline`.

Do not record cookies, authorization headers, or sensitive account data.

## 6.4 Basic input-handling checks

In Burp Repeater, use a single quote as a basic input-handling probe.

For example:

```text
'
```

Also compare ordinary strings containing quotation marks with normal search terms.

Observe:

- Whether the application returns a normal response.
- Whether a generic validation message appears.
- Whether the application returns an unexpected server error.
- Whether internal database errors or stack traces are disclosed.
- Whether the response contains unexpected data.

A quote-related error is not sufficient evidence of SQL injection. Input validation, routing, or unrelated application errors may produce similar results.

Do not use data-extraction payloads, authentication-bypass payloads, destructive statements, or automated exploitation against an environment containing real data.

## 6.5 Review database access code

Inspect the server-side code that handles the tested input.

Look for:

- SQL statements assembled through string concatenation.
- Dynamic query construction using untrusted values.
- Database functions that concatenate user-controlled strings.
- Missing parameter binding.
- Excessive database privileges.

For PostgreSQL, use parameterized queries and properly designed database functions. If the application uses a Supabase client, review how filters and RPC calls are constructed and whether user-controlled values can alter query structure.

### Unsafe pattern

```text
"SELECT * FROM products WHERE name = '" + userInput + "'"
```

This example is unsafe because input is concatenated directly into SQL syntax.

### Safer pattern

Use a parameterized query supported by the database driver, with the value passed separately from the SQL statement.

The exact implementation depends on the database library and query interface used by the application.

## 6.6 SQL injection test cases

| Test ID | Test | Expected secure behavior |
|---|---|---|
| SQLI-01 | Normal search baseline | Expected products are returned |
| SQLI-02 | Single-quote input | Input is safely handled |
| SQLI-03 | Double-quote input | No unexpected query behavior |
| SQLI-04 | Malformed search value | Controlled validation response |
| SQLI-05 | Review input containing punctuation | Content is stored or rejected safely |
| SQLI-06 | Source-code query review | User input does not alter SQL structure |

## 6.7 SQL injection evidence

For every test, record:

- Test ID.
- Staging route.
- Parameter name.
- Test input.
- Expected behavior.
- Actual response.
- HTTP status.
- Sanitized screenshot or request/response.
- Relevant source-code location.
- Assessment result.

Classify a finding as confirmed only when there is reproducible evidence that user input changes query semantics beyond the intended behavior.

# 7. Cross-Site Scripting (XSS) Assessment

## 7.1 What is XSS?

Cross-site scripting occurs when untrusted content is interpreted by a browser as executable code in an application context.

Three common categories are:

- **Reflected XSS:** Input is returned in a response and interpreted by the browser.
- **Stored XSS:** Input is saved and later interpreted when another page displays it.
- **DOM-based XSS:** Client-side JavaScript processes untrusted data in an unsafe way.

## 7.2 Identify candidate input and output locations

Inspect the following staging features where available:

- Product search results.
- Product reviews.
- Contact messages.
- Profile fields.
- Product descriptions entered through administrative interfaces.
- Query parameters used by client-side JavaScript.

An input point is only a candidate. Confirm whether its data reaches a browser-rendered output context.

## 7.3 Establish a baseline

1. Open the staging application.
2. Search for an ordinary value.
3. Inspect the response and rendered page.
4. Open Firefox Developer Tools.
5. Inspect the relevant element in the DOM.
6. Record whether the value appears as text, an HTML attribute, or markup.
7. Save sanitized evidence as `XSS-01-baseline`.

## 7.4 Safe HTML rendering probe

In a staging field that displays user input, use a harmless markup probe:

```html
<b>ShopShield-XSS-Test</b>
```

Submit the value using synthetic data.

Inspect the result:

- If the page displays the literal markup, the content is being treated as text.
- If the browser renders the phrase in bold, the input has been interpreted as HTML.
- If the content is not displayed, determine whether it was rejected, transformed, or stored elsewhere.

Rendering HTML does not by itself prove XSS. The important question is whether an attacker can cause unsafe executable behavior in the relevant browser context.

## 7.5 Reflected XSS verification

For a candidate reflected input:

1. Establish a normal request baseline.
2. Send a harmless markup probe through the authorized staging route.
3. Inspect the raw response.
4. Inspect the browser-rendered DOM.
5. Determine whether the input is reflected and how it is encoded.
6. Review the source code that renders the value.
7. Document the outcome without using payloads that transmit data or affect other users.

If executable behavior needs to be demonstrated, use a dedicated local XSS lab or a disposable isolated test page rather than a shared customer-facing application.

## 7.6 Stored XSS verification

Stored XSS requires special care because saved content may be displayed to other users.

1. Create a disposable test record using a staging test account.
2. Submit the harmless markup probe from Section 7.4.
3. Open the page that displays the saved record.
4. Refresh the page and inspect the rendered DOM.
5. Review the rendering component and any sanitization logic.
6. Delete the synthetic record after collecting evidence.

Do not test persistent executable payloads in production reviews, shared profiles, or contact messages.

## 7.7 React implementation review

React normally escapes text rendered through JSX.

### Preferred text rendering

```tsx
<p>{review.comment}</p>
```

### Pattern requiring careful review

```tsx
<div dangerouslySetInnerHTML={{ __html: review.comment }} />
```

`dangerouslySetInnerHTML` requires a deliberate sanitization strategy when content is untrusted. Do not rely on client-side filtering alone.

Review:

- Whether HTML rendering is actually necessary.
- Whether a maintained HTML sanitizer is used.
- Whether the sanitizer is configured for the intended context.
- Whether untrusted values reach script-capable attributes or unsafe URL contexts.
- Whether client-side JavaScript uses unsafe DOM sinks.

## 7.8 XSS test cases

| Test ID | Test | Expected secure behavior |
|---|---|---|
| XSS-01 | Normal search baseline | Results render normally |
| XSS-02 | Harmless HTML probe | Content is handled as intended |
| XSS-03 | Reflected search input | Untrusted data is safely encoded |
| XSS-04 | Stored review content | Saved content is safely rendered |
| XSS-05 | Profile or contact field | Content does not execute as code |
| XSS-06 | Source-code rendering review | Unsafe HTML sinks are controlled |

# 8. Remediation Guidance

## 8.1 SQL injection remediation

- Use parameterized queries.
- Avoid concatenating untrusted values into SQL statements.
- Validate input types and allowed formats.
- Apply least-privilege database permissions.
- Review database functions for unsafe dynamic SQL.
- Return generic error messages to clients.
- Log diagnostic details securely on the server.
- Add regression tests for previously vulnerable inputs.

Input validation complements parameterization; it does not replace it.

## 8.2 XSS remediation

- Render user-controlled content as text wherever possible.
- Use context-appropriate output encoding.
- Sanitize HTML if rich-text rendering is a genuine requirement.
- Avoid unsafe DOM APIs and raw HTML injection.
- Validate URL schemes before using user-controlled URLs.
- Review content security policy as a defense-in-depth measure.
- Add regression tests for search, reviews, profile fields, and other affected components.

A Content Security Policy is an additional protection, not a substitute for safe rendering.

## 10. Severity and Risk Assessment

Rate findings based on demonstrated impact, exploitability, exposure, and the sensitivity of affected data.

- **Critical:** Severe compromise with broad, demonstrated impact.
- **High:** Significant unauthorized access or execution.
- **Medium:** Meaningful but constrained security impact.
- **Low:** Limited impact or defense-in-depth weakness.
- **Informational:** Observation without a demonstrated vulnerability.

Do not assign severity based only on an error message or the presence of a suspicious code pattern.

After testing:

- [ ] Remove disposable test records.
- [ ] Confirm production data remains unchanged.
- [ ] Remove temporary test accounts when no longer needed.

- [ ] Apply remediation changes in a controlled branch.
- [ ] Rebuild and deploy to staging.
- [ ] Repeat the original test cases.
- [ ] Confirm the expected secure behavior.
- [ ] Document any remaining limitations.
